### 1. Шар і правило залежностей

У процесі виконання лабораторної роботи було реалізовано чотиришарову архітектуру відповідно до принципів Clean Architecture.

- **Domain** — містить доменну сутність `Order`, об'єкт-значення `OrderItem` та інтерфейс репозиторію `IOrderRepository`. Цей шар не залежить від зовнішніх бібліотек і фреймворків.
- **Application** — містить DTO `CreateOrderDto` та сценарій використання `CreateOrderUseCase`, який реалізує процес створення замовлення.
- **Infrastructure** — містить реалізацію `InMemoryOrderRepository`, яка відповідає за збереження замовлень у пам'яті.
- **WebAPI** — містить контролер `CreateOrderController` та композиційний корінь `Container.ts` для реєстрації залежностей.

Напрямок залежностей організовано всередину: Application використовує абстракції Domain, Infrastructure реалізує інтерфейси Domain, а WebAPI відповідає за об'єднання компонентів. Відсутність зовнішніх залежностей у Domain підтверджено перевіркою його структури та імпортів вихідних файлів. Доменний шар використовує лише власні типи та стандартні засоби TypeScript.

### 2. Сценарій використання

Основний сценарій використання — `CreateOrderUseCase`, розташований у `src/Application/use-cases/CreateOrderUseCase.ts`. Сценарій приймає через конструктор порт `IOrderRepository`, який використовується для збереження створеного замовлення. Під час виконання сценарію створюються об'єкти `OrderItem` та `Order`. Доменна перевірка відхиляє замовлення, яке не містить жодного товару. У такому випадку помилка виникає до виклику репозиторію. Таким чином, бізнес-логіка не залежить від конкретної реалізації механізму збереження даних.

### 3. Композиційний корінь

Для керування залежностями використано бібліотеку Awilix. Реєстрація компонентів виконується у файлі `src/WebAPI/Container.ts`.

| Абстракція / компонент  | Реалізація                | Життєвий цикл | Обґрунтування                                    |
| ----------------------- | ------------------------- | ------------- | ------------------------------------------------ |
| `IOrderRepository`      | `InMemoryOrderRepository` | Singleton     | Спільний екземпляр сховища замовлень             |
| `CreateOrderUseCase`    | `CreateOrderUseCase`      | Scoped        | Один екземпляр сценарію в межах області запиту   |
| `CreateOrderController` | `CreateOrderController`   | Transient     | Новий екземпляр контролера при кожному отриманні |

Для створення окремої області залежностей використовується функція `createRequestScope()`.

### 4. Модульні тести

Для перевірки сценарію `CreateOrderUseCase` створено три модульні тести з використанням Vitest.

1. **`успішно створює та зберігає замовлення`** — перевіряє створення замовлення та виклик методу збереження репозиторію.
2. **`не зберігає замовлення з некоректними даними`** — перевіряє відхилення замовлення без товарів і відсутність виклику репозиторію.
3. **`передає помилку репозиторію далі`** — перевіряє передавання помилки залежності без її приховування.

Замість реального репозиторію використано ручні заглушки на основі `vi.fn()`.
