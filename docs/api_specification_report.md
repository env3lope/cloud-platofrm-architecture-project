## Проєктування та специфікація API (REST OpenAPI 3.0 та gRPC Proto3)

## 1. Архітектурне позиціонування інтерфейсів

У межах архітектури E-Commerce Cloud Platform передбачено два типи API для забезпечення взаємодії між клієнтами та мікросервісами системи.

- **Публічний REST API** (`api/openapi.yaml`) — призначений для взаємодії зовнішніх клієнтів, зокрема Web App і Mobile App, із сервісом замовлень (OrderService). Для нього важливі зрозуміла структура запитів і відповідей, сумісність із різними клієнтськими платформами, використання HTTPS/JSON та стандартизована обробка помилок відповідно до RFC 7807.
- **Внутрішній gRPC API** (`api/service.proto`) — призначений для взаємодії OrderService з InventoryService. Основними вимогами є строга типізація повідомлень, компактність переданих даних, швидкість обміну та підтримка потокової передачі інформації. Для цього використовується Protocol Buffers 3 поверх HTTP/2.

Обидва контракти розроблено вручну за принципом **Contract-First**, тобто специфікації API визначено до реалізації програмної логіки сервісів.

## 2. Специфікація REST API (OpenAPI 3.0.3)

Для опису публічного API сервісу замовлень створено специфікацію `api/openapi.yaml` із використанням OpenAPI 3.0.3.

У специфікації визначено такі кінцеві точки:

| Метод  | Шлях                | Призначення                                                         | Коди відповідей    |
| ------ | ------------------- | ------------------------------------------------------------------- | ------------------ |
| GET    | `/orders`           | Отримання списку замовлень із пагінацією та фільтрацією за статусом | 200, 400, 401      |
| POST   | `/orders`           | Створення нового замовлення                                         | 201, 400, 401, 422 |
| GET    | `/orders/{orderId}` | Отримання інформації про конкретне замовлення                       | 200, 401, 404      |
| PATCH  | `/orders/{orderId}` | Оновлення статусу замовлення                                        | 200, 401, 404, 422 |
| DELETE | `/orders/{orderId}` | Скасування замовлення                                               | 204, 401, 404, 422 |

У контракті використано три типи параметрів:

- **Path parameters** — `orderId` для ідентифікації конкретного замовлення.
- **Query parameters** — параметри пагінації та фільтрації, зокрема `page`, `limit` і `status`.
- **Request body** — об'єкти `CreateOrderRequest` та `UpdateOrderStatusRequest` для передавання даних під час створення й оновлення замовлень.

Для DTO-схем визначено типи даних, обов'язкові поля, обмеження та приклади значень. Зокрема, використано `required`, `minimum`, `maximum`, `minItems`, `format` та `enum`.

### 2.1. Обробка помилок відповідно до RFC 7807

Для стандартизації помилок використано формат Problem Details відповідно до RFC 7807.

У `components/schemas` визначено схему `Problem`, яка містить поля:

- `type` — URI, що ідентифікує тип помилки;
- `title` — короткий опис помилки;
- `status` — HTTP-код відповіді;
- `detail` — детальніша інформація про помилку;
- `instance` — URI конкретного запиту або ресурсу, з яким пов'язана помилка.

Відповіді з помилками 4xx і 5xx використовують тип вмісту `application/problem+json`. Це забезпечує однакову структуру помилок незалежно від кінцевої точки API.

### 2.2. Автентифікація

Для захисту API визначено механізм Bearer Authentication із використанням JWT. Його описано в `components/securitySchemes`.

Токен передається в HTTP-заголовку `Authorization` у форматі `Bearer {token}`. Такий підхід дозволяє інтегрувати API із системою автентифікації Keycloak, що використовується в архітектурі платформи.

### 2.3. Валідація та тестування за допомогою Prism

Для перевірки OpenAPI-контракту використано Prism — інструмент для створення mock-сервера на основі специфікації OpenAPI.

Запуск mock-сервера виконується командою:

`npx @stoplight/prism-cli mock api/openapi.yaml -p 4010`

Після запуску сервер доступний за адресою `http://localhost:4010`.

Було перевірено основні сценарії взаємодії з API:

1. Створення замовлення за допомогою POST-запиту з коректними даними.
2. Надсилання запиту з некоректними даними для перевірки обмежень DTO та обробки помилок.
3. Отримання списку замовлень за допомогою GET-запиту з параметрами пагінації та фільтрації.

Prism використовує визначені в OpenAPI схеми для формування mock-відповідей, що дозволяє перевірити контракт без реалізації повноцінної серверної логіки.

## 3. Специфікація gRPC API (Protocol Buffers v3)

Для внутрішньої взаємодії між OrderService та InventoryService розроблено gRPC-контракт із використанням Protocol Buffers 3.

Опис сервісу та повідомлень розміщено у файлі `api/service.proto`.

У контракті визначено сервіс `InventoryService`, який містить три RPC-методи:

| RPC                                                                                    | Тип взаємодії    | Призначення                               |
| -------------------------------------------------------------------------------------- | ---------------- | ----------------------------------------- |
| `CheckAvailability(CheckAvailabilityRequest) → CheckAvailabilityResponse`              | Unary            | Перевірка доступності товарів на складі   |
| `ReserveItems(ReserveItemsRequest) → ReserveItemsResponse`                             | Unary            | Резервування товарів для замовлення       |
| `StreamReservationUpdates(StreamReservationUpdatesRequest) → stream ReservationUpdate` | Server Streaming | Передавання оновлень статусу резервування |

Перші два методи використовують модель Unary RPC: клієнт надсилає один запит і отримує одну відповідь.

Метод `StreamReservationUpdates` реалізує Server Streaming, за якого клієнт надсилає один запит, а сервер передає потік повідомлень з оновленнями статусу резервування.

### 3.1. Структури повідомлень та типізація

У файлі `service.proto` використано такі можливості Proto3:

- базові типи `string`, `int64`, `double`, `bool`;
- тип `google.protobuf.Timestamp` для представлення часових міток;
- `repeated` для передачі списків товарів;
- вкладені повідомлення для структурування відповідей;
- `map<string, string>` для передачі метаданих;
- `enum` для визначення статусів резервування.

Для статусів резервування визначено перелічуваний тип `ReservationStatus`:

- `RESERVATION_STATUS_UNSPECIFIED = 0`;
- `RESERVATION_STATUS_PENDING = 1`;
- `RESERVATION_STATUS_RESERVED = 2`;
- `RESERVATION_STATUS_REJECTED = 3`;
- `RESERVATION_STATUS_RELEASED = 4`.

Нульове значення `UNSPECIFIED` відповідає вимогам Proto3 та використовується як значення за замовчуванням.

### 3.2. Генерація TypeScript-коду

Для генерації TypeScript-коду на основі Protobuf-контракту використано інструменти `grpc-tools` та `ts-proto`.

Згенерований файл розміщено у `gen/service.ts`.

Він містить типізовані інтерфейси повідомлень, методи серіалізації та десеріалізації, а також допоміжні функції для роботи з JSON-представленням даних.

Для повідомлення `BenchmarkOrder` згенеровано такі методи:

- `encode()` — перетворення повідомлення у бінарний формат Protobuf;
- `decode()` — відновлення повідомлення з бінарних даних;
- `fromJSON()` — створення повідомлення з JSON-об'єкта;
- `toJSON()` — перетворення повідомлення у JSON-представлення.

Згенерований код дозволяє використовувати визначені Protobuf-контракти у TypeScript-середовищі Node.js.

## 4. Порівняльний аналіз JSON та Protobuf

Для оцінювання ефективності двох форматів серіалізації проведено порівняння розміру однакового об'єкта замовлення у форматах JSON та Protobuf.

Тестовий об'єкт містить п'ять товарних позицій, ідентифікатори замовлення та покупця, адресу доставки, загальну вартість, метадані й часову мітку створення.

Для проведення експерименту створено скрипт `tools/benchmark.ts`.

Розмір JSON визначався за допомогою `Buffer.byteLength()` із кодуванням UTF-8. Розмір Protobuf визначався за довжиною бінарного повідомлення після виконання `BenchmarkOrder.encode()`.

### 4.1. Результати експерименту

За результатами виконання бенчмарку отримано такі показники:

| Метрика             |      JSON | Protobuf |
| ------------------- | --------: | -------: |
| Розмір повідомлення | 804 байти | 379 байт |

Ефективність передачі даних становить:

`Efficiency = JSON Size / Protobuf Size`

`Efficiency = 804 / 379 ≈ 2,12x`

Відсоток зменшення розміру:

`Reduction = ((JSON Size - Protobuf Size) / JSON Size) × 100%`

`Reduction = ((804 - 379) / 804) × 100% ≈ 52,86%`

Таким чином, Protobuf-повідомлення займає приблизно у 2,12 раза менше місця, ніж відповідне JSON-повідомлення. Економія обсягу переданих даних становить 52,86%.

### 4.2. Порівняння характеристик форматів

**Розмір повідомлень.** Protobuf використовує бінарне кодування та числові ідентифікатори полів замість текстових назв властивостей. Це дозволяє зменшити обсяг переданих даних. JSON є текстовим форматом, тому містить назви полів і текстове представлення значень.

**Швидкість серіалізації та десеріалізації.** Protobuf зазвичай ефективний під час кодування та декодування структурованих повідомлень, оскільки використовує бінарне представлення. JSON потребує текстового перетворення та парсингу. Фактична швидкодія залежить від реалізації, мови програмування та середовища виконання. У межах цього експерименту час серіалізації та десеріалізації окремо не вимірювався.

**Читабельність.** JSON легко переглядати та налагоджувати за допомогою звичайних інструментів, зокрема `curl`. Protobuf представлений у бінарному форматі, тому для перегляду його вмісту потрібна відповідна схема.

**Еволюція схем.** Protobuf підтримує еволюцію контрактів за умови дотримання правил сумісності. Номери тегів полів повинні залишатися незмінними. Для видалених полів рекомендується використовувати `reserved`, а нові поля повинні отримувати нові номери тегів. Це дозволяє різним версіям сервісів взаємодіяти без порушення сумісності.

**Транспорт.** REST API зазвичай використовує HTTP/1.1 або HTTP/2 для передачі JSON-повідомлень. gRPC працює поверх HTTP/2, який підтримує мультиплексування потоків в одному з'єднанні та стиснення заголовків HPACK. Це особливо корисно для потокової взаємодії між мікросервісами.

## 5. Висновки

У ході лабораторної роботи було спроєктовано публічний REST API та внутрішній gRPC API для E-Commerce Cloud Platform із використанням підходу Contract-First. Для REST API розроблено специфікацію OpenAPI 3.0.3, визначено кінцеві точки, параметри запитів, структури DTO, обмеження валідації та стандартизовані відповіді про помилки відповідно до RFC 7807. Для перевірки контракту використано mock-сервер Prism. Для внутрішньої взаємодії сервісів створено Protobuf-контракт із використанням Proto3. Визначено три RPC-методи, зокрема два Unary та один Server Streaming, а також типізовані повідомлення, вкладені структури й перелічувані типи. На основі контракту згенеровано TypeScript-код за допомогою `ts-proto`. Під час порівняння JSON та Protobuf встановлено, що розмір JSON-повідомлення становить 804 байти, а Protobuf — 379 байт. Це відповідає зменшенню розміру на 52,86% на користь Protobuf. Отримані результати підтверджують доцільність використання REST/JSON для публічної взаємодії із зовнішніми клієнтами, де важливі читабельність і простота інтеграції, та gRPC/Protobuf для внутрішньої взаємодії мікросервісів, де важливі строга типізація, компактність повідомлень і підтримка потокової передачі даних.
