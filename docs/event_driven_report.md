### 1. Каталог подій

У межах лабораторної роботи було створено два типи подій, які описують факти, що вже відбулися в системі.

| Подія                   | Видавець                                     | Споживачі                                                   | Поля                                                                |
| ----------------------- | -------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------- |
| `OrderCreatedEvent`     | `CreateOrderUseCase` через `IEventPublisher` | `InventoryReservationConsumer`, `OrderNotificationConsumer` | `eventId`, `occurredAt`, `orderId`, `customerId`, `totalAmount`     |
| `PaymentProcessedEvent` | Не підключений до сценарію публікації        | Не підключені                                               | `eventId`, `occurredAt`, `orderId`, `paymentId`, `amount`, `status` |

Кожна подія має унікальний ідентифікатор `EventId`, сформований за допомогою `randomUUID()`, та час виникнення `OccurredAt` у форматі UTC ISO 8601. Поля подій оголошені з модифікатором `readonly`, що забезпечує їх незмінність на рівні TypeScript.

### 2. Транспорт

Для передачі подій було обрано власну in-memory шину `InMemoryEventBus`, реалізовану без використання зовнішніх брокерів повідомлень. Такий варіант обрано через навчальний характер проєкту та відсутність необхідності розгортати додаткову інфраструктуру, наприклад RabbitMQ або Kafka.

Шина реалізує механізм публікації та підписки на події:

- `publish()` передає подію зареєстрованим обробникам;
- `subscribe()` дозволяє підписати обробник на певний тип події;
- обробники запускаються асинхронно;
- помилка одного обробника перехоплюється і не перешкоджає роботі інших.

Використано топологію **Broker (Publish/Subscribe)**. Видавець не знає про конкретних споживачів, а споживачі незалежно підписуються на потрібні типи подій через спільну шину. Це відрізняється від Mediator, оскільки видавець не адресує команду конкретному обробнику.

### 3. Видавець і споживачі

Публікація події виконується сценарієм `CreateOrderUseCase`.Після успішного збереження замовлення через `IOrderRepository` створюється `OrderCreatedEvent`, який передається через порт `IEventPublisher`. У такий спосіб Application-рівень не залежить від конкретної реалізації шини повідомлень.

Для обробки події `OrderCreatedEvent` реалізовано два незалежні споживачі:

1. **InventoryReservationConsumer** — імітує резервування товарів для замовлення та зберігає ідентифікатори зарезервованих замовлень у внутрішньому масиві.
2. **OrderNotificationConsumer** — імітує формування сповіщення про створення замовлення та зберігає ідентифікатори замовлень, для яких сформовано сповіщення.

Обидва споживачі підписуються на одну подію, але виконують незалежні операції. Додатково було перевірено ізоляцію помилок: тестовий обробник навмисно генерував помилку, проте інші споживачі продовжували роботу, а створене замовлення залишалося збереженим.

### 4. Ідемпотентність

Для забезпечення ідемпотентності реалізовано клас `InMemoryProcessedEventStore`. Оброблені ідентифікатори подій зберігаються у структурі `Set<string>`. Для кожного споживача створюється окремий екземпляр сховища. Перед виконанням операції споживач перевіряє, чи оброблявся відповідний `EventId` раніше. Якщо ідентифікатор уже присутній у сховищі, повторна обробка пропускається.Також використовується `Map<string, Promise<void>>` для відстеження подій, які вже перебувають в обробці. Це дозволяє уникнути одночасного виконання операцій для одного ідентифікатора.

Результат перевірки повторної доставки:

```
--- Створення замовлення ---
Товари зарезервовано для замовлення aa476f96-fc45-4561-a777-ef53f2479985
Сповіщення сформовано для замовлення aa476f96-fc45-4561-a777-ef53f2479985

--- Перевірка повторної доставки ---
Товари зарезервовано для замовлення aa476f96-fc45-4561-a777-ef53f2479985
Сповіщення сформовано для замовлення aa476f96-fc45-4561-a777-ef53f2479985
Дублікат події 373417bf-bc84-48b6-885f-993f5f0d157d пропущено
Дублікат події 373417bf-bc84-48b6-885f-993f5f0d157d пропущено

--- Результат ---
Кількість резервувань: 2
Кількість сповіщень: 2
Повторна доставка змінила стан резервування: false
Повторна доставка змінила стан сповіщень: false
```

Результати демонструють, що повторна доставка події з тим самим `EventId` не призводить до повторного виконання операцій споживачів.
