# ADR-0001. Вибір архітектурного стилю для E-Commerce Cloud Platform

## Статус

Accepted

## Контекст

Розроблювана система E-Commerce Cloud Platform повинна забезпечувати роботу каталогу товарів, кошика, оформлення замовлень, обробки платежів, управління складськими запасами та сповіщень. Платформа передбачає високі вимоги до продуктивності, масштабованості та надійності під час пікового навантаження. Водночас надмірна складність розподіленої інфраструктури може збільшити витрати на розробку та супровід системи.

## Рішення

Прийнято рішення використовувати **Мікросервісну архітектуру (Microservices)**. Функціональність системи буде розподілена між окремими сервісами: Catalog Service, Cart Service, Order Service, Payment Service, Inventory Service та Notification Service.

Кожен сервіс відповідатиме за окрему бізнес-область і взаємодіятиме з іншими сервісами через визначені API або асинхронні повідомлення. Розгортання сервісів виконуватиметься в контейнерах із використанням Kubernetes для оркестрації та автоматичного масштабування.

## Розглянуті альтернативи

- **Модульний моноліт (Modular Monolith):**
  - *Переваги:* простіше розгортання, налагодження та тестування, менші початкові інфраструктурні витрати.
  - *Недоліки:* неможливість незалежного розгортання модулів і обмежена можливість окремого масштабування компонентів. Відхилено через потребу в незалежному масштабуванні сервісів під час пікового навантаження.

- **Класичний моноліт (Layered Monolith):**
  - *Переваги:* проста структура застосунку та централізоване керування даними.
  - *Недоліки:* тісне зв'язування компонентів, складність незалежного масштабування та ризик ускладнення супроводу зі збільшенням функціональності. Відхилено через високі вимоги до масштабованості та модульності системи.

## Наслідки

- **Позитивні:**
  - Можливість незалежного масштабування сервісів відповідно до навантаження.
  - Ізоляція частини відмов у межах окремих сервісів.
  - Можливість незалежного розгортання та оновлення компонентів.
  - Спрощення розвитку окремих бізнес-доменів без необхідності розгортання всієї системи.

- **Негативні / Компроміси (Trade-offs):**
  - Збільшення складності інфраструктури, моніторингу та CI/CD.
  - Необхідність обробки мережевих помилок і забезпечення узгодженості даних між сервісами.
  - Ускладнення тестування та налагодження розподілених бізнес-процесів.
  - Додаткові витрати на контейнерну інфраструктуру й експлуатацію Kubernetes.
