# ADR-0002. Вибір СУБД для E-Commerce Cloud Platform

## Статус

Accepted

## Контекст

E-Commerce Cloud Platform обробляє структуровані дані про товари, користувачів, замовлення, платежі та складські запаси. Система повинна забезпечувати цілісність даних, підтримку транзакцій і коректність конкурентного виконання бізнес-операцій. Високе навантаження також вимагає ефективної індексації, оптимізації запитів і можливості подальшого масштабування сховища.

## Рішення

Прийнято рішення використовувати **PostgreSQL** як основну систему керування реляційними базами даних.

PostgreSQL забезпечуватиме зберігання структурованих бізнес-даних і підтримку транзакцій для критичних операцій, зокрема оформлення замовлень, резервування товарів та реєстрації платіжних операцій. Для підвищення продуктивності використовуватимуться індекси, оптимізовані SQL-запити та механізми кешування для часто запитуваних даних.

## Розглянуті альтернативи

- **MySQL:**
  - *Переваги:* зріла реляційна СУБД, підтримка транзакцій, широке поширення та наявність інструментів адміністрування.
  - *Недоліки:* відмінності в можливостях SQL, індексації та розширеннях порівняно з PostgreSQL. Відхилено на користь PostgreSQL як обраної основної платформи зберігання даних.

- **MongoDB:**
  - *Переваги:* гнучка документна модель і зручність зберігання даних зі змінною структурою.
  - *Недоліки:* необхідність окремого проєктування зв'язків і забезпечення цілісності взаємопов'язаних бізнес-даних. Відхилено через транзакційний характер операцій із замовленнями, платежами та складськими запасами.

## Наслідки

- **Позитивні:**
  - Забезпечення транзакційності та цілісності критичних бізнес-даних.
  - Підтримка складних запитів, індексації та зв'язків між бізнес-сутностями.
  - Спрощення резервного копіювання та відновлення завдяки використанню єдиної основної СУБД.
  - Можливість оптимізації продуктивності за допомогою індексів, кешування та реплікації.

- **Негативні / Компроміси (Trade-offs):**
  - Ризик виникнення вузького місця на рівні бази даних під час пікового навантаження.
  - Необхідність оптимізації запитів і контролю конкурентного доступу до даних.
  - Потреба в резервуванні, моніторингу та регулярному тестуванні відновлення.
  - Кешування потребує додаткової логіки інвалідації для запобігання використанню застарілих даних.
